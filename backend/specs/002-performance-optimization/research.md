# Phase 0 Research: Performance Optimization

Each decision below resolves one technical unknown from the plan's Technical Context, grounded in the actual codebase (`src/logs/repositories/log.repository.ts`, `src/logs/query-builders/aggregation-query.builder.ts`, `src/retention/retention.service.ts`, `src/config/database.config.ts` — all re-inspected directly during planning) and in the two prior analysis documents (`docs/performance_comparison_with_LogIngestion-majed.md`, `docs/suggestions_to_increase_the_performance.md`) rather than assumption.

## Decision 1: Write coalescing — in-process debounce queue in front of the existing `COPY` path

**Decision**: `LogRepository.insertMany()` no longer issues `COPY FROM STDIN` immediately per call. Incoming batches are pushed onto an in-memory queue; a short timer (default a few milliseconds, env-configurable) schedules a flush. Any other `insertMany()` call arriving before the timer fires joins the same flush, up to a configurable row cap. Each caller gets back a `Promise` that resolves only once *its* rows have been durably written as part of whichever flush absorbed them — the external `insertMany(logs: readonly NewLog[]): Promise<void>` signature and per-request `accepted`/`rejected` semantics in `LogIngestionService` do not change.

**Flush-loop and re-entrancy guard** *(remediates /speckit-analyze finding H1)*: a flush is driven by a loop, not a single drain: while the pending queue is non-empty, take one batch up to the row cap and flush it, then immediately check again — if rows are still queued (arrival outpaced one flush's cap), take and flush the next capped batch too, without waiting for a fresh debounce timer. Only once the queue is empty does the loop stop and the next `insertMany()` call schedule a new timer. A boolean in-flight flag guards against a debounce timer firing a second, concurrent flush loop while one is already running — a scheduled timer that fires while the flag is set is a no-op, since the running loop will itself pick up anything queued since it started. This prevents the queue from growing unboundedly under sustained arrival-rate-exceeds-single-flush-capacity load, which is exactly the condition this feature targets.

**A single caller's own rows are never split across two flushes** *(remediates /speckit-analyze finding F1 — HIGH)*: the row cap governs how many *different callers'* batches get merged into one flush, not the maximum size of any one caller's own batch. When building a capped batch, a caller already added to a non-empty batch is never partially included to stay under the cap — a caller is either fully included or deferred whole to the next flush. If a single caller's own batch by itself exceeds the cap, it is flushed alone, in its own `COPY`, exceeding the nominal cap for that one flush rather than being fragmented across two. `docs/Final_Project.md` documents no maximum `POST /logs` batch size, so an oversized single request is a real, reachable case, not a hypothetical — and splitting one caller's rows across two flushes would have no correct way to resolve that caller's single deferred `Promise`, since the two flushes could succeed and fail independently. Each caller's promise is resolved only once **every** row belonging to that caller has been part of a `COPY` that actually committed — never partially.

**Rationale**: This project's own measurements (`README.md:336`) show throughput dropping from ~20,400 to ~13,900 logs/sec as concurrency doubles from 8 to 16, with PostgreSQL CPU pinned at ~99.9% — i.e., the bottleneck is the *number of write transactions*, not the cost of any single one. `LogIngestion-majed`'s own README independently names the identical root cause ("a write per HTTP request saturates the single PostgreSQL CPU") and fixes it the same way. Merging concurrent requests into fewer, larger `COPY` calls directly reduces transaction count without touching any per-row cost.

**Alternatives considered**:
- Switch to `INSERT ... SELECT FROM jsonb_to_recordset()` (the reference project's exact mechanism) — rejected as the *underlying write*. `COPY` is still Postgres's fastest bulk-load path and is already proven in this codebase; the reference project's real insight is the coalescing, not its SQL shape. Coalescing composes with `COPY` just as well.
- PostgreSQL-level `commit_delay`/`commit_siblings` group-commit tuning only (already configured — `2000`/`5`) — insufficient alone: it batches the *fsync* of transactions that already separately reached Postgres, whereas application-level coalescing reduces the number of transactions reaching Postgres in the first place. Strictly more effective; keep the existing `commit_delay` tuning as a complementary, unrelated setting, not a substitute.
- No coalescing, rely on raising the write pool size only (Decision 10) — insufficient alone: more concurrent connections against a 1-CPU-limited Postgres container increases *contention*, not throughput, once CPU is the bottleneck (this exact false lead is already documented as measured-and-rejected in `docs/suggestions_to_increase_the_performance.md`'s "Measured and rejected" table, for the closely related read-pool case).

## Decision 2: Coalescing window and batch-size defaults

**Decision**: Debounce window defaults to a low single-digit millisecond value; the maximum rows merged into one flush defaults to a value in the low thousands. Both are environment-configurable (new constants in `src/common/constants/log-api.constants.ts`, following the existing `DEFAULT_LOG_RETENTION_DAYS`-style pattern of a named default plus an env-var override), not hardcoded, since the right values are a function of real request-size/concurrency patterns that should be tuned by measurement (spec.md FR-015), not fixed at design time.

**Rationale**: A few milliseconds is negligible against the 20-second ingest-to-queryable budget (SC-005) and against typical HTTP round-trip latency, while still being long enough to catch bursts of genuinely concurrent requests under load-generator-style traffic. Making both values configurable lets the load-testing process (FR-015/SC-008) sweep them without a code change, mirroring how `docs/suggestions_to_increase_the_performance.md` already recommends sweeping the write-pool size.

**Alternatives considered**: Hardcoded constants matching the reference project's exact values (2 ms / 2,048 rows) — rejected as a starting *default* is fine, but hardcoding with no override would violate FR-015's "validated by measurement" requirement and this project's own "prefer measured optimization over assumptions" principle (`CLAUDE.md`).

## Decision 3: Tenant safety of coalesced batches

**Decision**: No special handling is needed for mixed-tenant flushes. `tenant_id` is already resolved and stamped onto each `NewLog` object by `mapLogEntryToNewLog()` *before* `insertMany()` is ever called (per-request, inside `LogIngestionService.ingest()`), so a flush containing rows from multiple concurrent requests — potentially different tenants, or a mix of `AUTH_ENABLED=false` zero-config requests (all resolving to `DEFAULT_TENANT_ID`) and authenticated ones — still writes each row under its own already-correct tenant. Coalescing only ever merges already-tenant-stamped rows; it never resolves or infers tenant identity itself.

**Rationale**: Directly satisfies FR-004 and spec.md's Edge Case on this exact scenario. Confirmed by re-reading `src/logs/mappers/log.mapper.ts` and `src/logs/services/log-ingestion.service.ts` — tenant resolution happens strictly upstream of the repository layer that this feature touches.

**Alternatives considered**: Grouping/flushing per-tenant separately — rejected as unnecessary complexity; it would reintroduce more, smaller transactions under multi-tenant concurrent load, undermining Decision 1's entire point, for a safety property (tenant correctness) `COPY`'s per-row column list already provides for free.

## Decision 4: Rollup granularity — single tier, per minute

**Decision**: `log_rollups` stores one row per `(bucket, tenant_id, service, level)` at **one-minute** granularity only — no second-level tier.

**Rationale**: `GET /logs/aggregate`'s `bucket` parameter only ever accepts `1m`, `5m`, `1h`, or `1d` (`docs/Final_Project.md` line 259) — there is no requirement finer than one minute, unlike `LogIngestion-majed`'s two-tier (minute *and* second) design, which exists there specifically to shrink the raw-scan sliver for arbitrary `since`/`until` boundaries. A single per-minute tier already lets 5m/1h/1d buckets be answered by summing whole minute-rows with no raw scan at all when the requested range's `since`/`until` align to minute boundaries, and needs only a small raw-scan sliver (at most just under two minutes' worth of rows) for the general case. Adding a second tier would be complexity with no corresponding requirement — directly against `CLAUDE.md`'s "apply patterns only where they genuinely simplify the design."

**Alternatives considered**: Two-tier minute+second rollups (copying the reference project exactly) — rejected per above; not justified by this project's actual supported bucket sizes. Per-second-only rollups — rejected: far more distinct rows per tenant/service/level combination for no benefit, since nothing ever requests sub-minute buckets.

## Decision 5: Rollup key includes `tenant_id` — the one required adaptation, not a copy

**Decision**: `log_rollups`' primary key is `(bucket, tenant_id, service, level)` — `tenant_id` included from the start, not bolted on later.

**Rationale**: `LogIngestion-majed` has no tenants, so its rollup key is `(bucket, service, level)`. Copying that key verbatim would let two tenants' counts for the same bucket/service/level collide and combine under `ON CONFLICT ... DO UPDATE SET count = count + EXCLUDED.count` — a direct violation of FR-007/SC-006 and the base project's tenant-isolation guarantee. This is the single clearest example in this feature of "adapt, don't copy": the technique (pre-aggregation) transfers; the exact schema does not, because the reference project has one fewer axis of correctness to protect.

**Alternatives considered**: A separate `log_rollups` table per tenant — rejected: unnecessary operational complexity (dynamic table creation/migration per self-registered tenant) for no benefit over a single shared table with `tenant_id` as a leading key column, which is exactly the pattern already established for `logs.tenant_id` itself (research.md Decision 6 in `specs/001-multi-tenancy`).

## Decision 6: Rollup upsert mechanism — same connection, same transaction as `COPY`

**Decision**: After each coalesced flush's `COPY` completes, the repository computes per-`(tenant_id, service, level, minute-bucket)` counts from the in-memory batch it just wrote (a simple JS grouping pass over the same array already held in memory — no extra query), then issues one small `INSERT INTO log_rollups (...) VALUES (...), (...), ... ON CONFLICT (bucket, tenant_id, service, level) DO UPDATE SET count = log_rollups.count + EXCLUDED.count` covering however many distinct groups that flush touched (typically a handful, not thousands). **Both the `COPY` and this `INSERT` run inside one explicit transaction on the same checked-out connection** — `BEGIN` before `COPY`, `COMMIT` only after the rollup `INSERT` also succeeds; any failure in either statement rolls back both. `log_rollups` is a normal **`LOGGED`** (durable) table, not `UNLOGGED` — see Decision 8 for why this specific pairing (atomic transaction + a durable table) is what eliminates the rebuild-consistency problem entirely, rather than just narrowing it.

**Rationale** *(remediates /speckit-analyze finding C1 — CRITICAL)*: the original version of this decision described `COPY` and the rollup `INSERT` as two independent statements. If the process crashed between the two — `COPY` committed, rollup upsert not yet run — `logs` would durably have the rows while `log_rollups` silently undercounted them, with no trigger to detect or correct it (the table wouldn't be "empty," just quietly wrong), directly violating FR-005's "numerically identical to a full scan" and FR-009's "must never report an incorrect count." Wrapping both statements in one transaction makes that failure mode structurally impossible: Postgres guarantees the pair either both survive a crash or neither does. `COPY` running inside an explicit `BEGIN`/`COMMIT` block on the same connection is standard, well-supported Postgres behavior — no different from any other multi-statement transaction. `LogRepository`'s `copyLogsIn()` already holds a raw checked-out `PoolClient` for the duration of one flush, so issuing `BEGIN`/`COMMIT` on that same client costs nothing structurally new.

**Consequence for Decision 8**: this fix, combined with `log_rollups` being a durable (not `UNLOGGED`) table, means `log_rollups` can *never* drift out of sync with `logs` due to an application crash or an unclean Postgres restart — both tables are written together, atomically, from the moment this feature is deployed forward. The only remaining reason `log_rollups` could ever need populating from scratch is a **one-time historical backfill** for `logs` rows that existed *before* this feature's code was deployed (which, by definition, never had a live upsert applied to them) — a fundamentally different and much simpler problem than "recover from a crash while traffic is live," addressed in the rewritten Decision 8 below.

**Alternatives considered**:
- Making `log_rollups` `UNLOGGED` for extra write speed (matching `LogIngestion-majed`) — rejected: Postgres automatically truncates `UNLOGGED` tables after an unclean shutdown. Combined with an atomic COPY+upsert transaction, an `UNLOGGED` `log_rollups` would still lose data on a crash even though the atomicity fix prevents it from ever being *individually* inconsistent with `logs` — it would just be *entirely wiped*, reintroducing exactly the "needs a rebuild mechanism, safe under concurrent ingestion" problem this decision is designed to avoid. A `LOGGED` table costs the normal WAL overhead any other durable table pays, which is already accepted for `logs` itself under this project's durability requirements (FR-002/FR-003) and is not a new category of cost.
- A second `SELECT tenant_id, service, level, date_trunc('minute', timestamp), COUNT(*) ... GROUP BY ...` query against `logs` immediately after the `COPY`, instead of computing the group counts in application code — rejected: strictly more expensive (a full extra query, re-reading rows the process already has in memory) for the same result, independent of the atomicity question.

## Decision 7: Aggregation query strategy — rollup-first with raw-scan fallback

**Decision**: `buildAggregationQuery()` (or a new sibling builder it delegates to) checks whether the request has no `q`/`attr.*` filter. If so, it reads `log_rollups` for the portion of `[since, until)` that aligns to whole minutes, and falls back to a direct scan of `logs` only for the (at most two, one on each end) partial-minute slivers — unioning and re-summing the two result sets, the same shape as `LogIngestion-majed`'s approach but two-way instead of three-way (Decision 4). Any request with a `q`/`attr.*` filter, which no rollup can answer, is served exactly as today — a full raw scan, unchanged. **The rollup-read query applies `WHERE tenant_id = :tenantId` unconditionally**, the same discipline `applyLogFilters()` already enforces as the very first predicate against `logs` — ideally by extracting/reusing that same tenant-scoping helper rather than hand-writing a second, independent `tenant_id` predicate against `log_rollups` that could drift out of sync with it over time.

**Rationale**: Satisfies FR-005/FR-006/SC-003/SC-004 directly: the common case's cost stops scaling with total row count, while the filtered case's correctness is untouched because it never consults `log_rollups` at all. The explicit tenant-filter requirement *(remediates /speckit-analyze finding H3 — HIGH)* closes a gap the original version of this decision left implicit: Decision 5 makes `log_rollups`' **schema** tenant-safe (the PK includes `tenant_id`), but a correct schema does not guarantee a correct query against it — nothing about the table's shape stops a query from reading rows for every tenant in a bucket and summing them together. `applyLogFilters()`'s unconditional, always-first `tenant_id` predicate exists specifically to make that class of mistake structurally hard against `logs`; the rollup-read path needs the identical guarantee, stated explicitly rather than assumed from the schema alone.

**Alternatives considered**: Materialized views refreshed on a timer — rejected: introduces staleness (violates FR-005's "numerically identical to a full scan" requirement, and directly conflicts with SC-005's 20-second-queryable target for anything not yet refreshed) that an incrementally-upserted table (Decision 6) avoids entirely.

## Decision 8 (revised): One-time historical backfill via migration — no rebuild service, no readiness flag

**Decision** (supersedes the original "non-blocking `LogRollupRebuildService`" design — see below for why): `log_rollups` is populated for pre-existing `logs` rows by a **new migration** — a single `INSERT INTO log_rollups (...) SELECT bucket, tenant_id, service, level, COUNT(*) FROM logs GROUP BY ... ON CONFLICT (bucket, tenant_id, service, level) DO UPDATE SET count = log_rollups.count + EXCLUDED.count` — run exactly once, the same way every other schema change in this project runs: via TypeORM's existing `migrationsRun: true` mechanism, before `app.listen()` is ever called. There is no application-level rebuild service, no `OnApplicationBootstrap` hook for this, and no runtime "is it safe to trust rollups yet" check anywhere in the read path.

**Why this replaces the original design, and why the FR-019 principle it protects still holds** *(remediates /speckit-analyze findings C2 and C3 — both CRITICAL; FR-009/FR-019 have since been rewritten in spec.md to match this design directly — see "Consequence for spec.md" below)*:

The original design assumed `log_rollups` could become stale *after every unclean restart* and built a non-blocking background-rebuild service to cope with that. Decision 6's atomicity fix removes that premise entirely: once `COPY` and the rollup upsert commit together, in one transaction, against a durable (`LOGGED`) table, `log_rollups` can never drift out of sync with `logs` from an application or database crash — there is no more "stale after restart" scenario to rebuild from. The *only* remaining reason `log_rollups` would ever need populating from scratch is a one-time historical gap: rows already sitting in `logs` from before this feature's upsert-on-ingest code existed, which by construction never had a live upsert applied to them. That is a migration-shaped problem, not a runtime-concurrency problem, and folding it into a migration is strictly simpler than the service it replaces:

- **Provably correct under concurrent ingestion, not just probably correct.** Migrations run before `app.listen()`, which is before the process accepts any HTTP traffic — there is no concurrent writer to race against during the backfill statement. Its `GROUP BY` reads a `logs` table nothing else is modifying at that moment; correctness doesn't depend on reasoning about interleavings, snapshot timing, or a readiness watermark, because there is nothing running concurrently to interleave with. This directly satisfies the requirement to choose "the simplest design that can prove correctness under concurrent ingestion" — the proof is that concurrency is structurally absent from the one operation that could have raced.
- **No readiness signal needed on the read side.** Because the backfill completes (as part of "migrations applied") before the app is reachable at all, `log_rollups` is *always* fully consistent with whatever `logs` contains by the time any request — including the very first one — can reach `aggregation-query.builder.ts`. There is no window where a query could observe a partially-populated rollup table, so there is nothing for the query path to check.
- **Does not reintroduce the risk the original Clarifications answer was protecting against.** That decision worried about a rebuild-driven `GET /health` stall on a large dataset happening on *every* restart. A backfill migration only does real work (a full `GROUP BY` scan) the *one time* it's first deployed against a database that already has pre-existing `logs` rows — and Final_Project.md's own zero-config grading scenario (`docker compose up` against a fresh database) has an *empty* `logs` table when this migration runs, making the backfill an instant no-op in exactly the scenario that's actually graded. Every restart *after* that first deploy does no rollup-related work at all beyond the normal "are migrations applied" check every migration already requires — which is the same readiness condition `GET /health` already gates on today, for every other schema change in this project.
- **The no-new-readiness-dependency principle is satisfied by construction, not by a special case.** The original Clarifications answer's underlying intent was that `GET /health` must never gain a new thing to block on because of rollup work. Under this design there is no distinct "rollup-rebuild status" concept at all — populating `log_rollups` is just part of "migrations applied," the same existing readiness condition that already governs every other piece of schema/seed state in this project (including, precedent-setting, `specs/001-multi-tenancy`'s tenant tables). `GET /health` behaves exactly as it does today; nothing new is added to what it waits on.

**Consequence for spec.md** *(updated per /speckit-analyze finding F2)*: the original version of this note argued FR-009/FR-019 didn't need editing because they were "satisfied trivially" by this design. On reflection that was the wrong call — FR-009's *literal* text ("summaries are lost or become unavailable... MUST rebuild... in the background") and FR-019's *literal* text ("MUST NOT block on rebuilding... independent of rollup-rebuild status") both describe a runtime rebuild mechanism that this design deliberately does not have. Leaving those requirements worded that way — even if the design happens to satisfy them vacuously — would misdescribe the actual system to any future reader (or grader) checking the spec against the implementation. **spec.md's FR-009 and FR-019 have been rewritten** to describe what the system actually guarantees: atomic same-transaction updates to `log_rollups` (FR-009, first half), one-time migration-based historical backfill (FR-009, second half), and no new `GET /health` readiness dependency (FR-019) — with no reference to "rebuild" in either. The Clarifications 2026-08-13 entry is preserved as a historical record (a real question was asked and answered at the time) with a follow-up "Resolution update" note explaining the mechanism was later simplified and why the *principle* it established (no new blocking dependency on rollup state) still holds under the new design.

**Alternatives considered**:
- The original non-blocking `OnApplicationBootstrap` rebuild service — superseded as above; correct in intent (don't block health on a large scan) but solving a problem (post-crash staleness) that Decision 6 eliminates, at the cost of a genuinely hard concurrency problem (see next two bullets) the migration-based approach never has to solve.
- A watermark/"rebuilt-through" marker letting the read path distinguish already-rebuilt buckets from not-yet-rebuilt ones, with the background service advancing it — rejected after closer analysis: this only resolves the *read side's* ignorance of rebuild progress (finding C2); it does not, by itself, prove the *rebuild's own writes* can't double-count or lose a concurrent live upsert (finding C3), which requires additional reasoning about statement-level snapshot timing versus row-lock ordering that a background rebuild racing live traffic cannot avoid needing. The migration-based design sidesteps needing that proof at all, rather than constructing and verifying it.
- Blocking startup on a background rebuild (mirroring `LoadgenKeySeeder`'s seed-before-ready pattern) — this is effectively what the migration-based approach does anyway (migrations already block `app.listen()`), just using the mechanism this project already trusts for exactly this kind of "must be consistent before the app is reachable" requirement, instead of a bespoke service.

## Decision 9 (revised): Rollup pruning at retention time — bulk-delete expired buckets, delta-subtract the boundary bucket (never replace)

**Decision**: `RetentionService.runMaintenance()` gains two additional steps, both under the *same* `pg_try_advisory_lock` call it already acquires (no second lock, no second scheduled job):

1. **Fully-expired buckets** (`bucket` strictly before the retention cutoff's minute): unconditionally bulk-deleted — `DELETE FROM log_rollups WHERE bucket < :cutoffMinute`. This is safe *(rationale corrected per /speckit-analyze finding F3)* even though a log with an old timestamp can legitimately be ingested at any time — `docs/Final_Project.md`'s validation rule only rejects timestamps more than five minutes in the *future*; there is no lower bound, so a backfilled or late-arriving old log landing in an already-expired bucket is a real, allowed case, not a validator-rejected one. The delete is safe regardless: it is unconditional and re-evaluated fresh on every retention run, so any such row (and the `log_rollups` contribution its own atomic upsert just created for that bucket) is simply swept on the *next* run, the same way any other data that crosses the retention threshold between runs already is. No special-casing of "how old can an incoming log be" is needed for correctness.
2. **The one boundary bucket** straddling the cutoff (the single minute where `deleteExpiredRows()`'s straggler delete removes *some* but not necessarily *all* of that bucket's rows): adjusted by a **negative delta**, computed and applied in the same atomic statement that performs the deletion — `WITH deleted AS (DELETE FROM logs WHERE timestamp >= :bucketStart AND timestamp < :bucketEnd AND timestamp < :cutoff RETURNING tenant_id, service, level), deltas AS (SELECT tenant_id, service, level, COUNT(*) AS removed FROM deleted GROUP BY 1, 2, 3) UPDATE log_rollups SET count = log_rollups.count - deltas.removed FROM deltas WHERE log_rollups.bucket = :bucketStart AND log_rollups.tenant_id = deltas.tenant_id AND log_rollups.service = deltas.service AND log_rollups.level = deltas.level`. The rollup's count is *decremented by exactly the number of rows this statement itself just deleted*, never recomputed from an independent `SELECT COUNT(*)` and never replaced with an absolute value.

**Rationale** *(remediates /speckit-analyze finding M2 — MEDIUM)*: the original version of this decision said the boundary bucket is "recomputed... from whatever logs rows remain," without specifying whether that recompute was additive or a replace. A replace is unsafe under concurrent ingestion: if a late-arriving log (nothing in this system constrains how far in the *past* a log's timestamp may be — only "not more than five minutes in the future" is validated) lands in the boundary bucket and its own live-upsert transaction commits in a narrow window relative to retention's read-then-write, a naive "read the current count, then write that value" replace can silently overwrite the concurrent increment, undercounting by exactly the late row. Framing retention's adjustment as a **relative delta** (subtract precisely what this statement deleted) instead of an absolute replace makes it commute correctly with the live path's own relative delta (add precisely what that flush inserted) regardless of execution order — both are `UPDATE ... SET count = count ± N` against the same row, and Postgres's normal row-level locking on `UPDATE`/`INSERT ... ON CONFLICT DO UPDATE` already serializes concurrent modifications to that row correctly (each transaction applies its own delta on top of whatever the row's value is at the moment it acquires the row lock, in whichever order the two transactions actually commit) — there is no scenario in which one delta is silently lost, because neither side ever writes an absolute value computed from a snapshot that could be stale by the time it's applied.

**Rationale (continued)**: satisfies FR-008/FR-014. Re-reading `src/retention/retention.service.ts` confirmed `deleteExpiredRows()` already exists as a straggler-row safety net alongside `partitionService.dropExpiredDailyPartitions()`; folding the count adjustment into the *same* `DELETE ... RETURNING` statement that performs that straggler delete (rather than a separate `SELECT COUNT(*)` beforehand) removes the read-then-write gap entirely, not just narrows it.

**Alternatives considered**:
- Recompute-and-replace from a fresh `SELECT COUNT(*)` (the original version of this decision, and the pattern `LogIngestion-majed`'s own `refreshRollupsAtRetentionBoundary` uses) — rejected per the race described above; safe only in the reference project because it has no concept of a live upsert racing retention in the first place at that granularity being examined here.
- A separate scheduled job for rollup pruning — rejected: would need its own lock and its own cadence decision for no benefit over piggybacking on the maintenance job that already runs on the right cadence and already holds the right lock.

## Decision 10: Explicit write-pool sizing

**Decision**: `createDatabaseOptions()` in `src/config/database.config.ts` gains `extra.max`, sourced from a new `DB_WRITE_POOL_MAX` env var with a documented default, mirroring `createReadDatabaseOptions()`'s existing `DB_READ_POOL_MAX` pattern exactly.

**Rationale**: Directly closes the gap `docs/suggestions_to_increase_the_performance.md` §2 already identified and this plan's own re-inspection of `database.config.ts` confirmed still exists: the write/default connection has no `max` at all, silently defaulting to node-postgres's built-in 10, while the read pool is explicitly configured. Satisfies FR-018.

**Alternatives considered**: None meaningfully — this is a one-line gap with an already-established sibling pattern to follow; the only open question is the default value, deferred to measurement (sweep 10/20/30, per the existing suggestions doc) rather than fixed here.

## Decision 11: Migration strategy

**Decision**: The removal of `logs.attributes_text` and its GIN index is **folded into the original migrations that created them** (`1785684350114-CreateLogsTable.ts` and the migration that added `idx_logs_attributes_text_gin`), not layered as a new `DROP COLUMN` migration. `log_rollups` gets a **new** migration, since there is no existing migration about rollups to fold into.

**Rationale**: Consistent with the pre-release fold convention already established and used repeatedly in this project (`specs/001-multi-tenancy/research.md` Decision 11; this session's own `created_at` removal from the `tenants` table followed the identical pattern) — nothing has shipped to a real deployment yet, so there is no upgrade path to preserve by layering a reversible migration on top.

**Alternatives considered**: A new `DROP COLUMN attributes_text` migration — rejected per the established convention; would leave the original `CreateLogsTable` migration permanently describing a column that no longer exists, misleading anyone reading migration history as the current schema definition.

**Already-migrated databases** *(remediates /speckit-analyze finding H2 — HIGH)*: folding a change into an already-applied migration's file only changes what a *fresh* database ends up with — TypeORM tracks completed migrations by name/timestamp in `typeorm_migrations`, not by re-diffing file content, so any database that already ran the original (pre-edit) `CreateLogsTable` migration will silently keep its `attributes_text` column forever; the edited migration file will never re-run against it. This exact class of drift required a `DROP SCHEMA public CASCADE` reset during `specs/001-multi-tenancy`'s own implementation, for the same reason. This feature must not repeat that surprise silently: any environment already migrated before this feature lands — including the database this project's own prior live-verification sessions have been using — needs either a full reset (acceptable, per this project's own established pre-release convention, for a local/dev database with no real data to preserve) or a manual, explicitly-run `ALTER TABLE logs DROP COLUMN attributes_text; DROP INDEX idx_logs_attributes_text_gin;` before the folded migration's file will actually match reality. This applies only to the `attributes_text` removal (an edit to an *existing* migration); it does not apply to the new `log_rollups` table or its backfill (Decision 8), since those are entirely new migrations that run correctly regardless of a database's prior migration history.

## Decision 12: Explicitly rejected / out-of-scope techniques (carried forward from the comparison report)

**Decision**: The following, already evaluated in `docs/performance_comparison_with_LogIngestion-majed.md`, remain out of scope for this feature and MUST NOT be introduced:

- **`synchronous_commit=off`** — violates FR-002/FR-003 and `docs/Final_Project.md`'s "never respond 200 to a batch you have not durably accepted."
- **Batched-`DELETE`-based retention** (replacing partition-drop) — would be a regression; `partition.service.ts`'s `DROP TABLE` approach is already architecturally superior (O(1) vs. O(n), no bloat) to the reference project's own retention design. Not touched by this feature at all beyond the rollup-pruning addition in Decision 9.
- **Swapping NestJS/TypeORM for Fastify/Prisma, or Zod for hand-rolled validation** — disproportionate, high-risk rewrites for marginal gains secondary to Decision 1's actual bottleneck; conflicts with `CLAUDE.md`'s "preserve the existing architecture... unless a requirement explicitly requires a change."
- **PostgreSQL version bump (16→17) and the `q=` planner-hint technique** — genuinely plausible per the comparison report, but not named in this feature's spec.md FRs or in the user's stated priorities for this plan (write coalescing, rollups, query/write overhead reduction). Left as unscoped future work rather than folded in here, to keep every task in `tasks.md` traceable to a specific FR.
