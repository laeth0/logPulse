# Research: Optional Backpressure Support

## Decision 1: Where admission control lives, and why no new sequencing code is needed

**Decision**: The admission check runs as the very first thing inside `LogRepository.insertMany()`, immediately after the existing `if (logs.length === 0) return Promise.resolve();` guard and before anything is pushed onto `pendingInserts`.

**Rationale**: `LogIngestionService.ingest()` (`src/logs/services/log-ingestion.service.ts`) already validates the raw batch, splits it into `validLogs`/`rejected`, and calls `this.logRepository.insertMany(validLogs.map(...))` exactly once, with exactly that request's validation-accepted entries. By placing the check inside `insertMany()` rather than in the service or controller, three of spec.md's requirements are satisfied automatically, with no new sequencing/ordering code:

- **FR-005** ("capacity check runs only after per-entry validation"): `insertMany()` is never called with anything but already-validated entries — there is no earlier code path that reaches it.
- **FR-006** ("capacity check counts only validation-accepted entries"): the array `insertMany()` receives *is* the validation-accepted array; nothing else is ever measured.
- **FR-009** ("auth/tenant resolution runs before the capacity check"): `ApiKeyAuthGuard` already runs before the controller method body, which is already before `LogIngestionService.ingest()`, which is already before `LogRepository.insertMany()` — the existing Nest guard pipeline already fully precedes this new check without any change.

**Alternatives considered**: A separate `AdmissionControlService` injected into `LogIngestionService`, called explicitly before `insertMany()` — rejected per the user's explicit instruction to keep admission/capacity ownership close to the existing `LogRepository` queue, and because it would require `LogIngestionService` to duplicate knowledge of the queue's internal row/byte accounting that `LogRepository` already owns, or to receive it via a second collaborator — unnecessary indirection for two integers and two comparisons.

**Note**: this decision covers *where the check runs*, not what it throws. `checkAdmission()` throws plain, HTTP-agnostic domain errors — see Decision 8 for the translation step that turns those into the `413`/`503` responses described in Decision 3 below.

## Decision 2: Capacity signal — two independent dimensions, tracked on `LogRepository` itself

**Decision**: Two private mutable counters on `LogRepository`: `pendingRowCount` and `pendingByteCount`. Both are incremented, synchronously, at the moment a caller's batch is pushed onto `pendingInserts` (admission time) and decremented, synchronously, at the moment that same caller's `PendingInsert` entry is settled — resolved or rejected — inside `flushBatch()`'s existing per-entry loops. This means the counters cover the entire "admitted but not completed" window per spec.md's Clarifications: time spent sitting in `pendingInserts` (queued) *and* time spent inside an active `takeBatch()`/`flushBatch()` transaction that hasn't committed yet (in-flight) — a caller's rows are still "pending" from the moment `insertMany()` admits them until its Promise actually settles, exactly matching the existing code's own definition of when a caller's request is "done" (research.md Decision 1 of `002-performance-optimization`).

Row count is simply `logs.length`. Byte count is estimated once per batch by summing already-materialized field lengths directly — `entry.message.length + entry.service.length + entry.tenant_id.length`, plus each attribute's key/value lengths, plus a small fixed per-entry constant covering the timestamp and JSON structural punctuation (`{}`, `":"`, `,`, quotes) that isn't otherwise accounted for — **not** `JSON.stringify(entry)` followed by `Buffer.byteLength()`.

**Rationale**: Reuses exactly the state-lifecycle boundary the existing coalescing code already has (`PendingInsert` already tracks a caller's rows from push to settle) — no new lifecycle to reason about, just two more numbers tracked across the same boundary. Two independent dimensions (not one combined score) is required because the two failure modes are genuinely different: many small entries can exhaust row count long before byte size matters, and a few entries with very large `message`/`attributes` payloads can exhaust byte size long before row count matters. `docs/Final_Project.md` sets no maximum entries-per-batch and no per-entry message/attribute size cap, so both are real, independently reachable conditions — not hypothetical.

The field-length approach is chosen specifically *instead of* `JSON.stringify`+`Buffer.byteLength` because the latter is real, avoidable cost on the ingestion hot path once this feature is enabled: a full string serialization (walking every field, allocating a new string) followed by a full UTF-8 re-scan of that string, per entry, on a container whose entire ingestion budget is 0.5 CPU — the same container `002-performance-optimization` spent an entire feature reducing per-row overhead on (raw-row reads instead of entity hydration, explicit pool sizing, dropping a redundant column). Summing string `.length` properties the entry already holds touches the same data without allocating or serializing anything new. This does mean the estimate uses UTF-16 code-unit counts rather than exact UTF-8 byte counts for non-ASCII content — an acceptable trade-off given spec.md's Assumptions already require only an *estimate*, not an exact on-disk footprint, and the alternative (paying full serialization cost for UTF-8 precision) is exactly the cost being avoided.

**Alternatives considered**: A single combined "weighted units" score (e.g., `rows + bytes/1024`) — rejected as it would make the *reason* for a rejection ambiguous (operators tuning the limits couldn't tell which dimension actually saturated) for no simplification, since two independent `if` comparisons cost nothing extra. Computing byte size from the raw HTTP request body instead of the mapped `NewLog` array — rejected: the raw body includes entries that validation already rejected (contradicts FR-006), and mapping happens before `insertMany()` is reached regardless. `JSON.stringify(entry)` + `Buffer.byteLength()` (the original design) — rejected per the cost analysis above; it's measurably more expensive than the field-length sum for the same estimate-grade precision, on exactly the path this project has repeatedly found worth optimizing at this granularity.

## Decision 3: `413` vs `503` — reusing this project's existing oversized-request precedent

**Decision**: `checkAdmission()` (on `LogRepository`) performs two comparisons, in order, throwing a plain domain error in either failing case — not an HTTP exception; see Decision 8 for how each becomes an actual status code:

1. **Absolute check** (independent of current pending state): if the batch's own `rowCount > maxPendingRows` OR its own `byteSize > maxPendingBytes`, throw `IngestionBatchTooLargeError` — this batch could never be admitted, at any pending level, including zero. `LogIngestionService`'s translation step (Decision 8) turns this into `PayloadTooLargeException` (413).
2. **Headroom check** (only reached if the absolute check passes): if `pendingRowCount + rowCount > maxPendingRows` OR `pendingByteCount + byteSize > maxPendingBytes`, throw `IngestionCapacityExceededError(retryAfterSeconds)` — this batch would fit on its own, but other admitted-but-not-completed work is temporarily occupying the remaining headroom. The translation step turns this into `BackpressureException` (503, carries `retryAfterSeconds`).

**Rationale**: The `413`-vs-`503` split itself was directly resolved in spec.md's Clarifications session by inspecting this project's own precedent: `JSON_BODY_LIMIT` (`src/main.ts`) is enforced by the body parser and already surfaces as `413` through `GlobalExceptionFilter`'s existing `getExternalClientError()` passthrough, not a retryable `5xx` — because retrying an oversized body can never succeed. The same logic applies here: a batch whose valid entries alone exceed the configured maximum will *always* exceed it, load or no load, so signaling it as `503`/"temporary, retry later" would be actively misleading to a well-behaved client that honors `Retry-After`. `503` is reserved exclusively for the case that is actually temporary — where the identical request, retried once other work drains, can succeed. *Which class* carries that meaning (a plain error here vs. an HTTP exception) is a separate, later decision — see Decision 8.

**Alternatives considered**: Returning `503` for both cases (simpler, one exception type) — rejected as it violates the "never respond in a way that invites a retry that can't possibly help" principle the project's own `JSON_BODY_LIMIT` precedent already establishes, and would fail SC-008. Returning `400` for the too-large case — rejected: `400` is already the established status for *validation* failures (malformed/invalid entries) in this project's contract; conflating "your data is malformed" with "your batch is too large for this deployment's configured capacity" would blur an existing, well-defined distinction.

## Decision 4: Exception design and the generic `Retry-After` pass-through

**Decision**: `BackpressureException` (`src/logs/exceptions/backpressure.exception.ts`) extends `ServiceUnavailableException` and exposes a public readonly `retryAfterSeconds: number`. It is constructed only by `LogIngestionService`'s translation step (Decision 8), never by `LogRepository`. `GlobalExceptionFilter.catch()` gains a small, generic check, applied **only within its existing `instanceof HttpException` branch** (i.e., only after `status`/`message` have already been resolved from a real `HttpException`) — for whether the caught exception carries a numeric `retryAfterSeconds` property (structural/duck-typed check, e.g. `typeof Reflect.get(exception, 'retryAfterSeconds') === 'number'`), and if so calls `response.set('Retry-After', String(retryAfterSeconds))` before writing the JSON body.

**Rationale**: `GlobalExceptionFilter` today has zero imports from any feature module (`logs/`, `tenancy/`, etc.) — it is purely generic, working only with `HttpException`/`Error`. A duck-typed property check preserves that: `common/` never needs to import from `logs/` to support this one exception type, and the same mechanism transparently supports any *other* future exception (e.g., a future rate-limiter's `429`) that wants a `Retry-After` header, without the filter needing to know about it by name. `PayloadTooLargeException` needs no such treatment — it already flows through the filter's existing `HttpException` branch unchanged, producing `{"error": "<message>"}` with no extra header, exactly per FR-018.

**Why scoped to `instanceof HttpException` specifically**: `IngestionCapacityExceededError` (Decision 8's domain error) also carries a `retryAfterSeconds` property, by design — it's where `BackpressureException` copies the value from. If the duck-typed check ran unconditionally (before determining whether the exception is even an `HttpException`), a domain error that ever reached the filter directly — e.g., a future call site to `LogRepository.insertMany()` that bypasses `LogIngestionService`'s translation — would get a `Retry-After` header attached to what should be a generic `500 Internal Server Error`, incorrectly implying the request is safe to retry. Scoping the check to the branch that has already confirmed `exception instanceof HttpException` closes this: a plain `Error` subclass (which `IngestionCapacityExceededError` deliberately is — see Decision 8) can never take this path, regardless of what properties it happens to expose.

**Alternatives considered**: Setting the header directly in `LogsController`/`LogIngestionService` via a caught exception and manual `@Res()` handling — rejected: `logs.controller.ts`'s `ingest()` method today only manually handles the success/400 path (a *resolved* promise); duplicating response-shaping logic `GlobalExceptionFilter` already centralizes for every other rejection (`401`/`403`/`429`/`413` already flow through it untouched) would be redundant. An unconditional duck-typed check (the original design) — rejected per the coupling risk above, once the existence of a same-shaped domain error made it a real, not just theoretical, hazard.

## Decision 5: Why no lock, semaphore, or atomic-counter library is needed

**Decision**: The check-then-increment sequence in `insertMany()` (read `pendingRowCount`/`pendingByteCount`, compare, and — if admitted — increment them and push onto `pendingInserts`) requires no explicit concurrency-control primitive.

**Rationale**: Node.js executes JavaScript on a single thread; `insertMany()`'s admission-check-and-push sequence contains no `await` between reading the counters and updating them, so it runs as one atomic unit relative to every other concurrently-arriving `POST /logs` request — two "simultaneous" requests are still handled one at a time, in some order, by the event loop, and each one's check-then-push is indivisible. This is the exact same property the existing coalescing code already depends on for its own `isFlushing` boolean guard (`runFlushLoop()`) and its `takeBatch()` shift-based draining — no lock has ever been needed there either, for the same reason.

**Alternatives considered**: An explicit mutex/semaphore library — rejected as solving a race condition that cannot occur in this runtime model; would add a dependency and complexity for zero behavioral benefit, directly contradicting `CLAUDE.md`'s "avoid unnecessary complexity" and the user's explicit "avoid unnecessary abstractions" instruction.

## Decision 6: Configuration — naming, defaults, and reusing the existing size-string convention

**Decision**: Four new environment variables, all optional, all defaulting to values that keep the feature fully inert:

| Variable | Default | Meaning |
|---|---|---|
| `BACKPRESSURE_ENABLED` | `false` | Master switch (FR-002) — when unset/false, `insertMany()` skips every check in this feature entirely; behavior is byte-for-byte identical to before this feature. |
| `BACKPRESSURE_MAX_PENDING_ROWS` | `20000` | Absolute + headroom row-count limit (FR-016). Starting default, pending measurement — at the coalescing window's steady-state arrival rate (5 ms window × 15,000 logs/sec ≈ 75 rows/window), this leaves generous headroom above normal operation while still bounding worst-case memory well inside the 256 MB app container limit. |
| `BACKPRESSURE_MAX_PENDING_BYTES` | `25mb` | Absolute + headroom byte-size limit (FR-016), parsed via the `bytes` package — same size-string format as the existing `JSON_BODY_LIMIT`. Sized to comfortably admit a few concurrent max-sized (`JSON_BODY_LIMIT`-capped, 10 MB default) request bodies before shedding, while leaving most of the 256 MB container budget for the Node/V8 baseline, HTTP layer, and DB connection buffers. |
| `BACKPRESSURE_RETRY_AFTER_SECONDS` | `1` | Fixed value sent in the `Retry-After` header on every `503` (spec.md Assumptions: a configurable fixed value, not a computed drain estimate). |

**Rationale**: Follows the exact pattern already established for `INGEST_COALESCE_WINDOW_MS`/`INGEST_COALESCE_MAX_ROWS` (`log-api.constants.ts`'s `DEFAULT_*` constants, overridable via env var, documented as starting points pending measurement — per `CLAUDE.md`'s "prefer measured optimization over assumptions"). Reusing `bytes` (already vendored transitively via `body-parser`) for the size-string format matches `JSON_BODY_LIMIT`'s existing convention exactly rather than inventing a second, different size-string parser or forcing operators to specify raw byte integers.

**Alternatives considered**: A single combined `BACKPRESSURE_MAX_PENDING` covering both dimensions via one number — rejected per Decision 2 (the two dimensions need independent limits and independent tuning). Raw-integer byte config (no size-string parsing) — rejected as inconsistent with `JSON_BODY_LIMIT`'s already-established, human-friendly convention for the same kind of setting in the same codebase.

## Decision 7: Explicitly out of scope (carried forward from spec.md FR-010/FR-017)

The following remain unimplemented in this version, per explicit instruction, and this research confirms no design decision above requires them:

- **DLQ, Kafka, Redis, RabbitMQ, or any external broker/queue** — rejection is synchronous and in-process; a rejected batch is simply never written, not redirected anywhere.
- **Adaptive CPU-based control, event-loop-lag monitoring, or DB-utilization/connection-pool-saturation signals** — admission is based solely on the two counters in Decision 2.
- **Complex per-tenant scheduling or quotas** — the counters are single, global instance fields with no tenant key, per FR-008.

## Decision 8: Domain-error / HTTP-exception layering

**Decision**: `LogRepository.checkAdmission()` never throws a NestJS `HttpException`. It throws one of two plain `Error` subclasses, defined in `src/logs/errors/ingestion-capacity.errors.ts` with **no import from `@nestjs/common`**: `IngestionBatchTooLargeError` (the absolute-limit case) and `IngestionCapacityExceededError(retryAfterSeconds)` (the headroom case). `LogIngestionService.ingest()` — which already calls `LogRepository.insertMany()` — wraps that call in a `try`/`catch` that translates each domain error into the corresponding HTTP exception: `IngestionBatchTooLargeError` → `PayloadTooLargeException` (413, built into `@nestjs/common`), `IngestionCapacityExceededError` → `new BackpressureException(error.retryAfterSeconds)` (503, Decision 4). Any other error from `insertMany()` (e.g., a genuine database failure, unrelated to backpressure) is re-thrown unchanged, exactly as it would propagate today.

**Rationale**: Directly required by an explicit engineering constraint: keep HTTP/error-response concerns out of repository logic. `LogRepository` is a persistence/queue-mechanics class — its job is to decide *whether* a batch can be admitted and *why not* (in domain terms: too large, or temporarily full), not to decide what HTTP status code that maps to. Putting the translation in `LogIngestionService` — the layer that already owns the ingestion request/response shape (it already builds the `{accepted, rejected}` response) — is the conventional place for a domain-outcome-to-HTTP-response mapping in this architecture, and it's a small, single-purpose addition (one `try`/`catch`), not a new abstraction. This also closes the coupling risk described in Decision 4: because the domain errors are plain `Error`s with zero NestJS awareness, they can never accidentally satisfy `GlobalExceptionFilter`'s `instanceof HttpException` check, however similarly-shaped they are to the HTTP exceptions they get translated into.

**Alternatives considered**: `LogRepository` throwing `PayloadTooLargeException`/`BackpressureException` directly (the original design) — rejected once evaluated against the "no HTTP concerns in repository logic" constraint; also created the Decision-4 coupling hazard, since NestJS's `HttpException` types are, by definition, HTTP-layer constructs with no natural home in a persistence class. A dedicated mapper/translator class or function — rejected as unnecessary indirection for a two-case `if`/`else if` translation that fits naturally as a few lines in the one method that already awaits `insertMany()`; would be the kind of abstraction introduced "for its own sake" this project's engineering principles explicitly discourage.
